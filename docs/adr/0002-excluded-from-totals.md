# 「不計入總時數」是 category 的當前屬性，不做歷史快照

有些 category 值得記錄卻不該算進「有效時間」，睡眠是最典型的例子。我們在 `categories` 加一個 `excluded_from_totals boolean not null default false`，讓這類時間照常被記錄、照常出現在統計列表中，只是不參與總和。

命名刻意寫成 `excluded_from_totals` 而不是 `excluded_from_stats`：被排除的只有總和，那些列在 summary 與 settlement 裡照常顯示。欄位名把這個範圍寫死，避免之後有人（或 agent）順手把整列也濾掉。也不用反向的 `counts_toward_totals`，因為程式裡最常出現的判斷是「跳過這個 category」，反向布林會讓每個判斷點都變成雙重否定。

## 為什麼不做快照

`planned_items.expected_minutes` 是快照，改動歷史紀錄不會回頭改寫已存的計畫。這個旗標**不套用**同一條原則，改動後所有歷史週與歷史月的總和立刻重算。

兩者保護的東西不同。計畫是一個歷史承諾，「我當初打算花 5 小時讀書」是既成事實。而「睡眠算不算有效時間」不是事實，是使用者對這個 category 的當前分類判斷。`categories` 上其他屬性早就都是即時的 —— 改名、改色、封存，歷史統計立刻反映新值，沒有一處存快照，旗標跟著同一套走才一致。

更關鍵的是使用情境。使用者打開這個旗標，幾乎必然是因為「睡眠一直在灌水我的統計」，而他打開後第一件事就是回頭看上個月。若歷史不變，這個功能在它最主要的用途上等於沒生效，使用者只能砍掉 category 重建 —— 而重建又會因為 entries 存在而只能封存。快照方案還要在每筆 entry 與每個 plan item 各多存一個布林，換來一個沒人要的行為。

代價是 AI retro 上週寫下的講法，可能跟這週重看時的數字對不上。retro 是當下的敘述而不是帳本，這個代價可以接受。

## 排除只活在統計層

旗標不下沉到執行層。timer 的 category 下拉照樣列出被排除的 category（否則根本無法為它計時），`ensureCalendarSession()` 的自動計時照常運作，plan board 照樣能排它。這跟 AGENTS.md 裡「category description 屬於管理與 AI 脈絡，不上執行面 UI」是同一種分層：category 帶著一些只對統計與管理有意義的屬性，執行面不看它們。

被排除的 category 仍可被排進週計畫，是刻意的。睡眠正是使用者想固定安排、也想知道自己有沒有做到的項目，看它的 Δ 有價值；只是這段時間不該算進「我這週投入了多少」。`computeAccuracy()` 的比值也照算，因為那是 per-category 的 actual/planned，本來就不牽涉跨類總和。

## 四個入口必須同時改

「總時數」在這個 codebase 裡由四處各自計算，彼此沒有共用口徑：`summarizePeriod()`、`computeWeekSettlement()`、首頁的兩張卡片、以及 `weekDayGaps()`。任何一處沒跟上，使用者會在首頁看到「今天記錄了 10 小時」、隔天在 week 頁看同一天卻只有 2 小時，而兩張畫面上都沒有線索能解釋差距。

所以實作不切成「先改 week 再改首頁」。四個入口在同一個 PR 裡改完，main 上不存在半套狀態。

## 總和要說出自己少算了多少

`PeriodSummary` 與 `WeekSettlement` 各多回一個被排除的分鐘數。理由是「仍然列出、只是不計入總和」必然帶來一筆文案債：使用者會把列裡的數字加起來，發現對不上總和，而他無從判斷差額是設計還是 bug。一個看起來像壞掉的數字，比一個明說自己少算了什麼的數字糟糕得多。差額在算總和的迴圈裡順手就拿得到，成本幾乎是零，而且為 0 時 UI 整個不顯示，沒設任何旗標的使用者看不到這個功能的痕跡。

同樣的數字也餵給 AI retro。LLM 拿到一堆分類數字會自己加總並寫進回顧，若不告訴它口徑，那個數字必然跟畫面對不上。
